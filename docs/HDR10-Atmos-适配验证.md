# HDR10 与 Dolby Atmos 适配验证

## 当前结论

2026-11-02 在 S85F（Tizen 9.0、Chromium 120）完成两轮真实片源实验。HDR10 和 Atmos 均未通过最终音画验收。第二轮已在 MSE 之前复现杜比音轨的响应截断，并验证包内退回 AAC 能保留播放位置和暂停状态。HDR／SDR 的人工卡顿结果仍保留，不能把所有卡顿归因于同一个问题。

按实施计划的停止条件，暂停产品入口与默认启用。当前分支 `codex/feature-hdr10-dolby-atmos` 从画质选择提交 `e4427630d45dacc93b3c92a251920c0c100bee7e` 创建，`app/` 保持该基线。不能把下述能力检测、媒体时间推进或测试包装记为功能落地。

## 已确认的产品选择

- HDR10 接入现有播放中画质菜单，并在设置页提供对应档位。首次使用保留现有默认值。
- 设备与片源支持时，允许在原画质上限下选择 HDR10。成功后再同步提高上限并记住偏好；失败时保留原设置。后续视频缺少 HDR10 时回退 SDR，保留偏好。
- Atmos 独立于画质，默认优先可用音轨。设置页提供开关，播放面板显示实际音轨状态。
- 验收使用电视扬声器及电视内已登录的大会员账号，不包含 eARC 透传或空间渲染验收。
- 复用 Shaka 4.12.5／MSE，不引入原生代理，不更换播放器。

## 第二轮对照与失败回退

用户要求继续后，测试改走应用完整播放流程。临时固定真实轨道，关闭弹幕和续播干扰；保存的设置不变。包内观测包含主线程采样、独立 Worker 心跳、原生 SourceBuffer 写入耗时，以及请求范围和响应长度。接收端只保存指定字段，不接收原始应用日志，也不保存媒体 URL、流签名或账号数据。

### 格式对照

| 场景 | 程序采样结果 | 验收边界 |
| --- | --- | --- |
| 同一 P2，4K HEVC SDR／AAC，30 秒 | 媒体时间约 23.698 秒，Shaka 缓冲时间约 6.808 秒，视频缓冲曾耗尽 | 用户报告间中卡顿，未通过连续音画验收 |
| 同一 P2，4K HEVC HDR／AAC，30 秒 | 媒体时间约 29.843 秒，Shaka 识别 PQ，缓冲时间约 0.979 秒 | 用户同样报告间中卡顿；未取得电视侧 HDR 状态确认 |
| `BV1eV411W7tt`，1080P HEVC／AAC，90 秒 | 媒体时间推进到约 88.553 秒，无 SDK 错误 | 属于程序对照，没有新增人工音画确认 |
| 同片源、同视频轨，仅改用 E-AC-3，90 秒 | 停在约 65.069 秒，多次网络错误和重载 | 仍未完成杜比音轨持续播放验收 |

四段主线程最大采样间隔为 310 ms～334 ms，未观察到秒级主线程停顿；没有 `QuotaExceededError`。原生 `appendBuffer` 最大同步耗时为 SDR 8 ms、HDR 51 ms、AAC 10 ms、E-AC-3 2 ms。这些数据不证明实际画面流畅，也不足以排除本轮未采到的停顿。

SDR 和 HDR 的 `decodedFrames` 均为 0，帧回调均只触发一次且 `mediaTime=0`，因此这些接口不用于本机的实际出画验收。首轮 HUD 显示的是媒体时间，视频等待缓冲时也会停；第二轮另列墙钟，并使用独立心跳，不能将首轮 HUD 停住直接认定为主线程卡死。

### 音轨响应截断

同一 E-AC-3 文件的请求 `bytes=5201866-5601317` 应得到 399,452 字节。Shaka 两次收到的实际正文均为 41,014 字节，而响应头仍声明完整范围。

原生 XHR 绕过 Shaka 后再次得到 HTTP 206、41,014 字节正文及 399,452 的 `Content-Length`。返回数据以 `moof` 开头。实际结束位置为：

```text
5,201,866 + 41,014 = 5,242,880 = 5 MiB
```

相邻范围 `bytes=4802414-5201865` 可完整返回 399,452 字节。单独请求边界前的 `bytes=5201866-5242879`，可完整返回 41,014 字节；边界后的 `bytes=5242880-5601317` 则为 HTTP 0。另一镜像返回 403，未获得可补齐的尾部数据。

这证明该样本存在交给 MSE 之前的音轨读取缺口。尚未区分 CDN、传输路径与电视 HTTP 栈，不能据此断言服务器文件本身损坏，也不能将这次失败归为 E-AC-3 解码器不支持。

同一网页取流接口分别请求 `platform=pc` 和 `platform=android`，返回的音轨地址都仍标记为 `platform=pc`，边界后读取都失败。因此本轮未采用修改平台参数的办法。

另外核查的 `BV14obQeoEr3`、`BV1zHZxBjEju` 和 `BV1J8411G7dB` 均提供杜比音轨元数据，但本轮测试的首选地址在头部及 5 MiB 后都返回 403；未穷尽其所有备用地址。`BV13K4y1b79t` 没有提供杜比音轨。这些样本不作为格式能力通过的证据。

### 包内回退实验

最后一轮仅在测试包装中加入响应完整性检查。发现上述不完整音轨时，阻止正文进入 MSE，并用同片源的真实 AAC 轨重建播放。保留原视频轨，读取当前播放位置及最新暂停状态；本次视频会话不再尝试该失败音轨。

| 场景 | 回退检查 | 后续结果 |
| --- | --- | --- |
| 播放中 | 在 50.122535 秒触发回退，请求与应用位置一致；选择实际 `mp4a.40.2` 音轨并继续播放 | 媒体时间推进到约 88.533 秒，越过原停播点，未出现新的 SDK 错误 |
| 暂停时 | 在 50 秒触发回退，重建后仍停在 50 秒，`paused=true` | 检查后由脚本主动恢复播放，推进到约 87.934 秒，未出现新的 SDK 错误 |

Shaka 4.12.5 在 Representation 中解析 JOC 声明。首轮探针只放在 AdaptationSet，不能把其 `spatialAudio=false` 直接解释成不支持 Atmos。回退探针已补充 Representation 声明，但本轮成功退回的是 AAC，不能据此接受 Atmos 输出。依据：[DashParser 源码](https://github.com/shaka-project/shaka-player/blob/v4.12.5/lib/dash/dash_parser.js)。

上述回退尚未接入产品。测试包装还没有覆盖新视频、迟到回调、切换期间再次按暂停／播放等全部边界。响应过滤位于请求重试之后，单纯在过滤器中抛错不能视为已经完成镜像重试或音轨回退；本轮使用明确的 AAC 回退动作。依据：[NetworkingEngine 源码](https://github.com/shaka-project/shaka-player/blob/v4.12.5/lib/net/networking_engine.js)。

七轮测试均已恢复并启动正常包，保存设置均未改变。证据断言为 27/27，含非零位置、暂停保位、实际 AAC 选择、越过旧停播点，以及七次恢复回执；这些断言不包含人眼音画验收。基线完整 `tools/check.sh` 再次通过，产品 `app/` 仍与 `e442763` 一致。

本轮脱敏遥测、汇总、断言脚本结果和回退实验包装位于 `dist/hdr-atmos-spike/round2/`。包内源码与构建、安装脚本保存在本机 `/private/tmp/bilibili-hdr-atmos-r2-20261102/`。最后一次正常包覆盖安装与启动均成功，未卸载、清登录或保存新的画质偏好。

## 继续实施的条件

1. 在可完整读取且缓冲充足的真实片源上继续验证 HDR 可见卡顿，并核实电视侧 HDR 状态。沿用独立心跳，不再把本机无效的帧计数当作成功或失败证据。
2. 查明杜比音轨跨 5 MiB 后读取失败的原因，或取得可完整播放的真实地址。不要重复用已知坏地址验证解码器，也不要把文件头 206 当成长播成功。
3. 将已验证的响应完整性检查与音轨分别回退纳入产品候选时，补齐跨视频、迟到回调和最新暂停／播放意图边界；回退试验本身不替代 Atmos 验收。
4. 获得持续音画及电视侧 HDR 状态的真实证据后，再接入产品菜单、设置、双端归一化和格式分别回退，并补全原计划中的离线、浏览器及真机验证。

能力 API 的适用范围见[三星 AVInfo 文档](https://developer.samsung.com/smarttv/develop/api-references/samsung-product-api-references/avinfo-api.html)。Shaka 的 Dolby 声明与配置见[Dolby 接入说明](https://professionalsupport.dolby.com/s/article/Dolby-Audio-and-Dolby-Vision-in-Shaka-Player)。两份文档均不保证本机实际播放成功。
