# HDR10 与 Dolby Atmos 适配验证

## 当前结论

2026-11-02 已接入 HDR10、Atmos 和分别回退，后续真机验收确认了电视侧 PQ 状态及真实 Atmos 持续有声、同步。用户在 HDR 段报告电视 Gamma 为 ST.2084；修复后的 Atmos 样本长播约 150 秒，65 次有效轨道采样全为 ec-3／JOC，没有回退 AAC。用户确认本轮持续有声、同步，操作后正常。HDR＋Atmos 同片源组合仍未通过，HDR 长测也保留过无进展回退的记录，不能宣称所有片源均流畅。

本轮另修复用户报告的“HDR 视频菜单缺少 HDR”：索引补读期间保留已发现候选；失败后保留 HDR10 项并标记本次不可用，禁止本会话重复尝试。短响应中的普通视频先交给现有强令牌接续，保留可用 Atmos；原生、强令牌和过期重取均保留最新暂停意图。完整门禁与浏览器复验通过，最终结果及边界见末节。

分支 `codex/feature-hdr10-dolby-atmos` 从 `e4427630d45dacc93b3c92a251920c0c100bee7e` 创建。前两轮暂停产品实现后，用户要求“完成修复”，本轮将已复现问题的修复接入候选代码。仍沿用 Shaka 4.12.5／MSE，没有增加播放器、代理或依赖。专项结束恢复测试前的正常包，不合并、不发布。前两轮人工卡顿结果继续保留；本轮仍观察到等待缓冲，不能声称卡顿全部消失。

## 已确认的产品选择

- HDR10 接入现有播放中画质菜单，并在设置页提供对应档位。首次使用保留现有默认值。
- 设备与片源支持时，允许在原画质上限下选择 HDR10。成功后再同步提高上限并记住偏好；失败时保留原设置。后续视频缺少 HDR10 时回退 SDR，保留偏好。
- Atmos 独立于画质，默认优先可用音轨。设置页提供开关，播放面板显示实际音轨状态。
- 验收使用电视扬声器及电视内已登录的大会员账号，不包含 eARC 透传或空间渲染验收。
- 复用 Shaka 4.12.5／MSE，不引入原生代理，不更换播放器。

### 音轨响应截断

同一 E-AC-3 文件的请求 `bytes=5201866-5601317` 应得到 399,452 字节。Shaka 两次收到的实际正文均为 41,014 字节，而响应头仍声明完整范围。

原生 XHR 绕过 Shaka 后再次得到 HTTP 206、41,014 字节正文及 399,452 的 `Content-Length`。返回数据以 `moof` 开头。实际结束位置为：

```text
5,201,866 + 41,014 = 5,242,880 = 5 MiB
```

相邻范围 `bytes=4802414-5201865` 可完整返回 399,452 字节。单独请求边界前的 `bytes=5201866-5242879`，可完整返回 41,014 字节；边界后的 `bytes=5242880-5601317` 则为 HTTP 0。另一镜像返回 403，未获得可补齐的尾部数据。

这证明该样本存在交给 MSE 之前的音轨读取缺口。尚未区分 CDN、传输路径与电视 HTTP 栈，不能据此断言服务器文件本身损坏，也不能将这次失败归为 E-AC-3 解码器不支持。

同一网页取流接口分别请求 `platform=pc` 和 `platform=android`，返回的音轨地址都仍标记为 `platform=pc`，边界后读取都失败。因此本轮未采用修改平台参数的办法。

另外核查的 `BV14obQeoEr3`、`BV1zHZxBjEju` 和 `BV1J8411G7dB` 均提供杜比音轨元数据，但本轮测试的首选地址在头部及 5 MiB 后都返回 403；未穷尽其所有备用地址。`BV13K4y1b79t` 没有提供杜比音轨。这些样本不作为格式能力通过的证据。

## 第三轮产品修复与验证

### 实现

- `api.js`：按设备能力请求 HDR／杜比位，不请求 Dolby Vision、8K 或无损音频。双端合并普通音频及 `dash.dolby.audio`；强令牌按文件路径、画质 ID 和编码 ID 匹配视频元数据，音轨按 ID 保留真实 codec。未知视频编码或尺寸不再用统一 HEVC 档位或尺寸表补写。Dolby 类型 2 的 30250／30255 才接受来源中的 Atmos 标记；缺失采样率／声道时读取 `dec3`，解析失败使用 AAC，不向 CDN 发送账号头。
- `settings.js`、`mpd.js`：默认仍为上限 120、自动画质。候选发现可包含 125，播放与预热仍受当前选择限制。Main10／HDR10 与 SDR 分组，AAC 与 E-AC-3 分组，ABR 不跨组；QN 125 的 Main10 按 HDR10 定义声明 BT.2020／PQ，首个片源文件头已核对一致。JOC 声明放在音频 Representation，采样率和声道使用来源信息或实际媒体配置。
- `player.js`：校验响应字节数，短响应不能进入 MSE；发生格式失败时只替换对应视频或音频，保持位置、最新暂停／播放意图和倍速。同一视频的失败预算跨内部重建保留，新视频清空；旧世代响应和排队回退不能改动新视频。无 HDR 的视频保留偏好并允许 SDR 自动选档。
- `app.js`、`index.html`：增加 HDR10 菜单和画质上限，成功选中实际 125 后才保存偏好及上限；增加默认开启的 Atmos 设置和实际音轨状态。HDR 选择先准备强令牌，避免将真实网页 403 误判为格式不支持。复用原有方向键与返回焦点。

### 本轮修复

**HDR 入口消失有两条原因。** 强令牌分批读取索引时，未完成索引的 HDR 轨道先从播放清单排除，菜单也跟着丢掉它；HDR 失败预算又把 125 从菜单彻底过滤。现在将 `hdrCandidates` 与可播清单分开。菜单保留真实候选，播放仍要求完整索引和解码支持。失败后显示“HDR10（本次播放不可用）”，移除其选择与方向键焦点，返回仍恢复画质入口。无 HDR 片源或设备能力不支持时仍不显示该项。

**普通视频短响应遗漏了强令牌接续。** 新找到的 Atmos 音轨可读，但同视频的普通视频流仍在 5 MiB 边界前截断。例如 30077 视频分段应有 966071 字节，实际仅 182436 字节。Shaka 将响应过滤错误包成 1007，原处理未能保留内层错误分类。修复后解开错误包装，音频失败按原规则退 AAC；普通网页视频短响应则一次性转既有强令牌路径，保留可读 Atmos。第 12 轮已覆盖实际短响应、强令牌恢复和后续长播。

原生退 DASH、强令牌重建与过期重取现在保留最新暂停意图。倍速按各播放路径实际支持范围处理。第 16 轮夹具曾在未进入播放前请求 1.5 倍速，设置未被接受，不能据此认定产品丢失倍速；后续改为原生支持的 2 倍速复验。第 17 轮实际进入 AVPlay 后接受 2 倍速；对本机不可达测试地址触发打开失败，恢复真实 DASH 后仍暂停在 20 秒、保留 2 倍速，恢复播放约 12 秒后推进到 41.946 秒。该项验证的是注入打开失败后的原生退路，不扩展为原生路径的 HDR 或 Atmos 播放验收。
